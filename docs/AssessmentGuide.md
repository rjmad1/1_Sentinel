# Assessment Reports Guide

This guide explains how to read and interpret the findings, risks, and recommendations generated by the EIIP assessment engine.

---

## 🔍 Finding Anatomy

Each finding generated by the assessment engine is structured to provide full operational context. When you expand a finding in the **Auditor** tab, you will see the following fields:

```
[Severity] Finding Title
  ├── Domain & Category: (e.g., Security - OS Configuration)
  ├── Priority Score: (Scale of 1 to 10, where 10 is highest priority)
  ├── Confidence Index: (Low, Medium, High)
  ├── Description: Detailed description of the anomaly.
  ├── Impact: The technical consequence if left unaddressed.
  ├── Business Risk: The operational or compliance consequence for the business.
  ├── Root Cause Hypothesis: Why this condition exists.
  ├── Recommended Remediation: Detailed instructions to resolve the finding.
  └── Verification Method: How to verify the fix was successful.
```

---

## 📊 Severity Levels

Findings are classified into four severity levels based on their potential impact on operations and security:

| Severity | Color | Description | Example |
| :--- | :---: | :--- | :--- |
| 🔴 **Critical** | Red | Active security holes, service outages, or hardware limits that halt operations immediately. | Antivirus disabled, C: drive out of space, public firewall disabled. |
| 🟠 **High** | Orange | Severe version drift, software with active high-severity CVEs, or critical stopped services. | Outdated Git/Nginx with CVE vulnerability, spooler service stopped but marked automatic. |
| 🟡 **Medium** | Yellow | Minor version drift, privilege sprawl (too many local administrators), or configuration warnings. | Four local administrators detected, minor application patch available. |
| 🔵 **Low** | Blue | Optimization suggestions, documentation warnings, or informational updates. | PowerShell runtime outdated, non-standard path locations. |

---

## 🎯 Confidence Index

The **Confidence Index** indicates the certainty level of the finding based on the collected evidence:
* **High**: Based on deterministic queries (e.g. registry values, file checksums, process lists). Very low chance of a false positive.
* **Medium**: Based on heuristics or environmental trends (e.g. capacity forecast predictions).
* **Low**: Based on indirect observations or incomplete logs. Requires manual validation by an engineer.

---

## 🧭 Interpretation Checklist

When reviewing a new assessment report, follow this workflow:

### 1. Address the Critical Red Flags
Sort findings by **Severity** and isolate **Critical** items.
- Focus on items with a **Priority Score** of 8 or above.
- Review the **Recommended Remediation** and copy the suggested shell command.

### 2. Evaluate Root Cause Hypotheses
Read the **Root Cause Hypothesis** to understand *why* the issue occurred, rather than just patching the symptom.
- *Example*: If a service is stopped, the hypothesis will tell you if it was manually disabled or if it crashed due to memory limits.

### 3. Review Business Risk
Translate the technical issue into business impact to justify change requests to leadership.
- *Example*: A disabled BitLocker status represents a compliance violation of the technical security baseline (SOX/GDPR), posing an data breach liability.

### 4. Verify Success
After executing a fix, check the **Verification Method** listed in the finding. This gives you the exact script or command to run to prove the issue is closed.
- Run a catalog **Re-Scan** in the Software tab to verify the updated state immediately.
